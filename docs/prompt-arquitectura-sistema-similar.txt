no el dominio RPBI. El negocio (residuos, manifiestos, SAT, etc.) es intercambiable.

reutiliza tal cual.

otro sistema con la misma arquitectura.

2. DOCKER — LÓGICA DE DISEÑO
================================================================================

Hay DOS compose files. Misma imagen PHP, distintos servicios según entorno.

2.1 Principio
- Un único Dockerfile (php:8.4-fpm) se reutiliza en 3 procesos:
  php-fpm (HTTP), horizon (workers), scheduler (cron Laravel).
- Nginx NO ejecuta PHP: solo sirve `public/` y hace FastCGI a php-fpm.
- MySQL y Redis tienen healthcheck. PHP/Horizon/Scheduler esperan
  `condition: service_healthy` antes de arrancar.
- El código se monta como volumen `./:/var/www/html` (hot reload de archivos).
- Red Docker interna: `appnetwork`. Los contenedores se hablan por NOMBRE
  de servicio (`mysql`, `redis`, `php`), no por localhost.

2.2 Dockerfile (imagen PHP)
FROM php:8.4-fpm
ARG INSTALL_XDEBUG=false

Extensiones instaladas (imprescindibles):
- pdo_mysql, mysqli  → BD
- pcntl              → OBLIGATORIO para Horizon (fork de workers)
- redis (pecl)       → cliente phpredis
- bcmath, exif, gd, intl, mbstring, opcache, soap, zip
- Composer 2 copiado desde imagen oficial

Xdebug es condicional (solo contenedor `php` de local, NUNCA en horizon/scheduler).
CMD por defecto: php-fpm (puerto 9000). Horizon y scheduler lo sobrescriben
con `command:`.

2.3 docker-compose.yml — LOCAL (todo incluido)

Servicios:
  nginx
    imagen: nginx:stable-alpine
    puerto host: ${PORT_NGINX:-8080} → 80
    volumes: código, docker/nginx/default.conf, logs, certs
    depends_on: php

  php
    build Dockerfile, INSTALL_XDEBUG=true (por defecto)
    working_dir /var/www/html
    volumes: código + docker/php/php.ini
    depends_on: mysql healthy + redis healthy

  horizon
    misma imagen, INSTALL_XDEBUG=false
    command: php artisan horizon
    depends_on: mysql healthy + redis healthy
    NO expone puertos (solo consume Redis)

  scheduler
    misma imagen, INSTALL_XDEBUG=false
    command: php artisan schedule:work
    (equivalente a un cron que corre `schedule:run` cada minuto)
    depends_on: mysql healthy + redis healthy

  mysql
    mysql:8.4
    charset utf8mb4 / collation utf8mb4_unicode_ci
    MYSQL_DATABASE=db, MYSQL_USER=user, MYSQL_PASSWORD=password, root/root
    puerto host: ${PORT_MYSQL:-4310} → 3306
    volumen persistente: mysql_data
    healthcheck: mysqladmin ping

  redis
    redis:8-alpine
    puerto host: ${PORT_REDIS:-6379} → 6379
    volumen persistente: redis_data
    healthcheck: redis-cli ping

  phpmyadmin
    PMA_HOST=mysql
    puerto host: ${PORT_PHPMYADMIN:-8081} → 80

Red: appnetwork (interna, creada por compose)
Volúmenes: mysql_data, redis_data
restart: unless-stopped

2.4 docker-compose-staging.yaml — STAGING/PROD (sin MySQL local)

Diferencias clave:
- NO hay servicio mysql ni phpmyadmin (la BD es externa al compose).
- Red `appnetwork` es EXTERNAL (ya existe en el host/servidor).
- php/horizon/scheduler solo esperan redis healthy (no mysql).
- restart: always
- XDEBUG_MODE=off en php/horizon/scheduler
- Nginx elige conf con ${NGINX_CONF_FILE:-default.conf}

Esto permite desplegar app+redis+horizon+scheduler en un servidor
mientras MySQL vive en otra máquina o contenedor ya existente.

2.5 Nginx (docker/nginx/default.conf)
- root: /var/www/html/public
- try_files → index.php (front controller Laravel)
- FastCGI a php-ban:9000 (NO usar "php:9000" si el container_name es php-ban;
  el default.conf actual usa el container_name)
- client_max_body_size 150M
- niega acceso a /.env

2.6 Makefile (atajos locales)
  make up       → docker compose down + up -d
  make install  → composer install dentro de php-ban
  make enter    → bash en php-ban
  make nginx    → sh en nginx-ban
  make clear    → config:cache/clear + horizon:terminate + queue:restart + route cache
  make ngrok    → túnel a localhost:8080

Tests / artisan SIEMPRE se corren DENTRO del contenedor:
  docker exec php-ban php artisan test
  docker exec php-ban php artisan migrate
  docker exec php-ban php artisan permissions:create
  docker exec php-ban php artisan roles:create
  docker exec php-ban php artisan initial-setup

2.7 Variables .env que Docker espera (local)

El .env.example de Laravel viene con sqlite/database. En Docker local hay que
apuntar a los NOMBRES DE SERVICIO:

  APP_URL=http://localhost:8080

  DB_CONNECTION=mysql
  DB_HOST=mysql          # nombre del servicio, NO 127.0.0.1
  DB_PORT=3306           # puerto INTERNO del contenedor
  DB_DATABASE=db
  DB_USERNAME=user
  DB_PASSWORD=password

  REDIS_CLIENT=phpredis
  REDIS_HOST=redis       # nombre del servicio
  REDIS_PORT=6379
  REDIS_PASSWORD=null

  QUEUE_CONNECTION=redis
  CACHE_STORE=redis      # o database; Horizon SÍ requiere Redis
  SESSION_DRIVER=database  # o redis

Sin QUEUE_CONNECTION=redis, Horizon arranca pero no procesa jobs útiles
(los jobs irían a la tabla `jobs` o sync).

3. REDIS + COLAS + HORIZON
================================================================================

3.1 Por qué Redis y no la cola `database`
- Horizon SOLO funciona con Redis.
- Redis da: workers auto-escalables, métricas, failed jobs UI, tags, balancing.
- El contenedor `horizon` es un proceso largo (`php artisan horizon`) que
  lee Redis y fork-ea workers PHP (por eso pcntl en el Dockerfile).

3.2 Conexiones Redis (config/database.php)
  client: phpredis
  default  → REDIS_DB=0   (colas + meta de Horizon)
  cache    → REDIS_CACHE_DB=1  (si CACHE_STORE=redis)

3.3 Colas definidas
Horizon supervisor-1 consume DOS colas:
  - default   → jobs genéricos (emails, notificaciones)
  - invoices  → facturación (más pesada / aislable)

Dispatch explícito a cola:
  SomeJob::dispatch(...)->onQueue('invoices');

3.4 config/horizon.php (puntos no negociables)
  use: 'default'          → conexión Redis
  path: /horizon          → dashboard
  waits: redis:default → 60s (alerta LongWait)
  memory_limit master: 64 MB
  workers:
    connection: redis
    queue: ['default', 'invoices']
    balance: auto
    autoScalingStrategy: time
    tries: 1
    timeout: 60
    memory worker: 128
    local maxProcesses: 3
    production maxProcesses: 10

3.5 Seguridad del dashboard Horizon
HorizonServiceProvider:
  Gate::define('viewHorizon') → $user->hasRole('Admin')
  /horizon queda detrás de sesión web + rol Admin.

3.6 Relación de procesos (importante)

  [HTTP php-fpm]  --dispatch job-->  [Redis lista]
                                          |
                                          v
                                   [contenedor horizon]
                                          |
                          +---------------+---------------+
                          |                               |
                    cola default                    cola invoices
                    (emails, etc.)                  (CreateInvoiceJob)

  [contenedor scheduler] cada minuto:
      php artisan schedule:run
      (jobs programados se DISPATCHAN a Redis; Horizon los ejecuta)

NUNCA correr `queue:work` a la vez que Horizon (compiten por los mismos jobs).
NUNCA meter Xdebug en el contenedor horizon (ralentiza workers).

3.7 Jobs actuales (patrón a copiar)
Ubicación preferida: app/Features/{Modulo}/Jobs/  o  Application/Jobs/

  DispatchInvoiceCreationJobs  (ShouldQueue)
    - Job "orquestador": busca servicios del día y despacha N CreateInvoiceJob
    - Pensado para Schedule (hoy comentado en routes/console.php)

  CreateInvoiceJob (ShouldQueue)
    - Recibe IDs (NO modelos serializados si no hace falta)
    - Inyecta casos de uso (CreateInvoice) + cliente HTTP externo (Facturapi)
    - Actualiza estado local tras la integración

  SendContractApprovalEmailJob (ShouldQueue, tries=3)
    - tags() para Horizon UI
    - respeta flags ENABLE_SEND_MAILS / DEFAULT_MAIL (no spamea en local)

  TestHorizonJob
    - smoke test: Log::info al procesarse

Patrón de job:
  implements ShouldQueue
  use Queueable
  constructor con IDs primitivos
  handle() con dependencias inyectadas por el contenedor
  onQueue('nombre') cuando no sea default

3.8 Scheduler (routes/console.php)
Hoy casi vacío (inspire + comentarios). El DISEÑO previsto:

  Schedule::job(new DispatchInvoiceCreationJobs)
      ->dailyAt('02:00');   // o everyMinute en pruebas

El contenedor `scheduler` YA está corriendo `schedule:work`.
Basta registrar el Schedule; no hay crontab en el host.

3.9 Comando de recarga tras deploy
  php artisan horizon:terminate
  (el contenedor tiene restart: unless-stopped/always → Horizon vuelve a subir
   con código nuevo)

Makefile `clear` ya hace: config cache/clear + horizon:terminate + queue:restart.

4. ARQUITECTURA DE APLICACIÓN (FEATURES)
================================================================================

4.1 Capas — qué va dónde

  app/Features/{Entity}/
    Application/     → casos de uso invocables (__invoke)
                       CreateX, UpdateX, DeleteX, SearchXHeaders, ListX
    Domain/          → SOLO si hay contratos/reglas (ej. InvoiceCommand)
    Infrastructure/  → SOLO si hay API externa o I/O no Eloquent
    Jobs/            → jobs de ese módulo

  app/Http/Controllers/Dashboard/  → páginas Blade del portal (CRUD)
  app/Http/Controllers/Admin/      → JSON Headers/DataTables del portal (sesión)
  app/Http/Controllers/Api/        → API móvil (Sanctum), NO el DataTable del portal

  app/Http/Requests/Admin/         → Form Requests (authorize + rules)
  app/Models/                      → Eloquent, fillable = columnas reales
  app/Mail/                        → mails
  app/Rules/                       → rules reutilizables

NO crear:
  - carpeta UseCases extra
  - controllers dentro de Features
  - repositorios/DTOs/mapeadores solo para pasar datos
  - LengthAwarePaginator en index (usar Headers + DataTables)

Controladores DELGADOS: validan/autorizan y llaman al caso de uso.
Eloquent SÍ se usa directo desde Application en CRUD simples.

4.2 Convención Headers (listados server-side)

Para CUALQUIER index de tabla:

  Application:
    Search{Entity}Headers  → usa BuilderFilter::paginate
    {Entity}Header         → proyección (opcional, readonly)
    {Entity}HeaderSearchResult

  HTTP:
    Admin\{Entity}HeadersController  → offset, limit, draw, order_by, order_direction
    Dashboard\{Entity}Controller     → index/create/store/edit/update/destroy (Blade)

  JS:
    resources/js/modules/{entidad}/index.js
    createDataTable('#entidad-table', columns, { ajax: fetch(...) })
    params: offset, limit, draw, order_by, order_direction
    respuesta: { draw, recordsTotal, recordsFiltered, data }

  Vista:
    card + table#entidad-table data-url="..." + tbody vacío
    NO @forelse, NO paginator Blade

  Rutas (grupo auth en web.php para CRUDs NUEVOS):
    Route::get('entity-headers', [EntityHeadersController::class, 'index']);
    Route::resource('entities', EntityController::class)->except(['show']);

Query compartida: app/Features/Shared/Query/
  QueryFilter, QueryOptions, BuilderFilter, QueryModifierInterface
  BuilderFilter::paginate clona el builder:
    1) count total
    2) count filtered (aplica FILTER, ignora offset/limit/order)
    3) get data con options
  Envelope DataTables lo arma el paginate (draw/recordsTotal/recordsFiltered).

FilterRequest (Admin) convierte query string + filters[] a QueryFilter/QueryOptions
con whitelist de campos (nunca filtrar columnas arbitrarias).

4.3 Rutas (bootstrap/app.php)

  web.php     → dashboard, CRUDs nuevos (drivers, services, manifests index)
  admin.php   → grupo extra con middleware web; hoy tiene users/roles/clients/
                zones/contracts + algunos headers legacy bajo prefix admin
  api.php     → API móvil Sanctum
  console.php → artisan commands + Schedule
  health      → GET /up

Middleware:
  trustProxies('*')  → HTTPS detrás de nginx/SSL
  alias Spatie: role, permission, role_or_permission

CONVENCIÓN ACTUAL PARA MÓDULOS NUEVOS (reglas Cursor):
  CRUD páginas → Dashboard\*  en web.php
  headers JSON → Admin\*HeadersController en web.php
  API móvil    → Api\* en api.php
  NO registrar resources nuevos en admin.php

Nota: el código histórico de clients/zones/contracts/users aún vive en Admin
y admin.php. Los módulos posteriores (drivers, manifests, services) siguen
el patrón Dashboard + Headers. Un sistema nuevo debe nacer YA con el patrón
nuevo, no con el legado.

4.4 Permisos
Constantes, nunca strings sueltos:
  app/Features/Permissions/Constants/PermissionTypes.php
    patrón: {entities}.view|create|update|delete  (+ extras de negocio)
  RoleTypes.php  → nombres de rol canónicos
  PermissionHandler → lista completa + etiquetas UI

Comandos de bootstrap:
  php artisan permissions:create   → sincroniza PermissionTypes a BD
  php artisan roles:create         → crea roles y syncPermissions
  php artisan initial-setup        → usuario admin@admin.com / admin

Form Requests: authorize() con PermissionTypes.
Vistas: ocultar botones sin permiso (UX); el servidor SIEMPRE autoriza.

4.5 Auth
Web: Fortify, guard web, redirect /dashboard, username=email.
API: POST /api/auth/login → { token_type, token, user }
     POST /api/auth/logout (sanctum)
     GET  /api/auth/user
     recursos protegidos: middleware auth:sanctum
User usa HasApiTokens + HasRoles + SoftDeletes.
Chofer: User hasOne Driver; la API de servicios del día filtra por zone_id
del Driver del usuario autenticado.

4.6 Frontend
Layout: resources/views/layouts/app.blade.php (Tabler page + header + alerts)
Partials: partials/dashboard/header.blade.php (menú)
Forms: x-form.input + iconos Tabler (ti ti-*)
HTTP admin: BanHttp.get / BanHttp.post en resources/js/admin.js (CSRF, loader)
DataTables: resources/js/shared/datatable.js
Cada módulo JS se registra en vite.config.js (input[]).
Paginación Blade (si se usa en algún lado): Bootstrap 5.
Si APP_URL es https://, AppServiceProvider fuerza URL::forceScheme('https')
para no romper @vite (Mixed Content).

4.7 Integraciones externas (patrón Command)
No llamar Guzzle desde el caso de uso a palo seco.

  Domain: interface InvoiceCommand { getPayload, getUrl, getMethod }
  Infrastructure: CreateCfdiCommand implements InvoiceCommand
  Shared/Infrastructure/{Proveedor}/{Proveedor}Client
    execCommand(Command): si FEATURE_ENABLED hace HTTP real;
    si no, responde stub (para local/tests sin credenciales)

Flags: FACTURAPI_ENABLED, FACTURAPI_SECRET_KEY, FACTURAPI_URI
Mails: ENABLE_SEND_MAILS, DEFAULT_MAIL

config/business.php: datos de empresa (razón social, direcciones) vía env,
NO hardcodeados. Un sistema nuevo debe tener su propio config/business.php.

5. FLUJOS TRANSVERSALES (independientes del negocio RPBI)
================================================================================

Estos flujos se copian cambiando nombres de entidad:

A) Alta con aprobación dual
   1. Usuario operativo captura entidad + configuración
   2. Envía a aprobación → job de mail a roles directivos
   3. Dos roles distintos deben aprobar (tabla *approvals* por rol)
   4. Al completar ambas: activa, cancela el registro previo ACTIVE
   5. Opcional: genera agenda/servicios del periodo del contrato

B) Generación masiva de "servicios/citas" a partir de un contrato
   BulkCreateX + DateGenerator
   frecuencias: weekly | biweekly | monthly
   ajusta sábados/domingos a día hábil
   por cada fecha: cabecera + detalles + documento asociado

C) Facturación asíncrona
   Scheduler despacha orquestador → N jobs en cola `invoices`
   cada job: persiste local + llama proveedor + guarda IDs externos + QR
   debe ser idempotente (reintentos)

D) API de campo (móvil)
   login Sanctum
   listado del día filtrado por zona/asignación del usuario
   token-push (registro de dispositivo; stub hoy)

E) Documentos PDF en el browser
   JS propio (jsPDF) para manifiestos/facturas; el index DataTable
   renderiza botones de acción en la columna actions (HTML en frontend,
   NO en el caso de uso).

10. FRONTEND HTTP Y UI (detalle operativo)
================================================================================

10.1 BanHttp (resources/js/admin.js)
ÚNICO cliente HTTP del panel. Axios preconfigurado:
  X-Requested-With: XMLHttpRequest
  Accept: application/json
  X-CSRF-TOKEN desde <meta name="csrf-token">

API global: window.BanHttp = { get, post, put }
  get(url, loaderText, params, headers, loader, timeout)
  post(url, data, loaderText, { params, headers, loader, timeout })
  put(...)

Muestra/oculta loader global (components/loader.js).
Toasts: showToast(type, text) append a .toast-container del layout.

NO usar axios suelto en módulos. DataTables del patrón nuevo usan `fetch`
en el ajax custom (sesión cookie via same-origin); BanHttp se usa para
modales, wizards y acciones puntuales.

app.js importa: Tabler + admin + permissions + users + roles.
Cada index de entidad se carga con @vite en @push('scripts'), NO en app.js
